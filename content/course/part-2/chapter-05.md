**Время:** 45–60 минут.

## Глоссарий главы 5

- **Rule** — постоянная инструкция, задающая рамки поведения агента.
- **`AGENTS.md`** — файл с инструкциями для AI-агента в проекте.
- **Глобальные инструкции** — настройки, действующие для разных проектов пользователя.
- **Проектные инструкции** — правила, относящиеся к конкретному репозиторию и доступные команде.
- **Prompt** — запрос для текущей задачи.
- **Ограничение** — правило, которое должно предотвращать нежелательное действие; текстовая инструкция сама по себе не является технической блокировкой.

## 5.1. Зачем нужны постоянные правила

В каждой задаче можно повторять: не выдумывай факты, отвечай по-русски, сохраняй термины, указывай источники, не меняй исходники без необходимости. Но такие инструкции занимают место и легко забываются.

Rules — постоянные инструкции, задающие общие рамки работы агента. В OpenCode основной проектный механизм — `AGENTS.md`. Он содержит сведения о проекте, договорённости, ограничения и ожидаемое поведение. Документация: https://opencode.ai/docs/rules/.

## 5.2. Rules, prompt, skill и документация

| Механизм | Для чего | Пример |
|---|---|---|
| Prompt | Текущая задача | «Проанализируй требования к уведомлениям» |
| Rules | Постоянные правила | «Не считать предположения фактами» |
| Skill | Повторяемая процедура | «Проведи интервью по требованиям» |
| Документация | Знания о системе | «Статусы описаны здесь» |
| MCP | Внешний инструмент или источник | Получить карточку задачи из трекера |

Не помещайте всю документацию в `AGENTS.md`. Это должен быть компактный набор правил и указателей, а не копия репозитория.

## 5.3. Что включать

Хорошие кандидаты: назначение проекта, структура репозитория, ссылки на ключевые документы, терминология, формат аналитических документов, правила работы с источниками, ограничения на изменение файлов и порядок проверки.

Не включайте секреты, длинные описания всех процессов, устаревающие сведения, противоречивые требования и инструкции, не относящиеся к проекту.

## 5.4. Пример AGENTS.md

Создайте в корне репозитория `AGENTS.md`:

```markdown
# Инструкции для AI-агента

## О проекте
Это учебный проект по анализу системы обработки заказов интернет-магазина.
Текущая задача — требования к уведомлениям пользователя при изменении статуса.

## Язык и стиль
- Пиши на русском языке.
- Используй точные и однозначные формулировки.
- Сохраняй термины, уже используемые в документах.

## Работа с источниками
- Не выдумывай факты о системе.
- Отделяй подтверждённые сведения от предположений и вопросов.
- Для существенных выводов указывай путь к исходному файлу.
- При противоречии источников зафиксируй его.
- Заметки со встреч не считать утверждёнными требованиями без подтверждения.

## Работа с файлами
- Перед изменением изучи связанные документы.
- Не перезаписывай исходники без явной необходимости.
- По возможности создавай черновик отдельно.
- Не изменяй файлы вне текущей задачи.
- Не создавай коммиты без отдельного запроса.

## Аналитические документы
- Используй Markdown.
- Для требований указывай уникальные идентификаторы.
- Не смешивай бизнес-цели, требования и варианты реализации.
- Критерии приёмки должны быть проверяемыми.
- Неизвестное отмечай как вопрос.

## Проверка результата
1. Перечисли изменённые файлы.
2. Проверь ссылки на источники.
3. Укажи допущения и открытые вопросы.
4. Проверь, что новые утверждения подтверждаются материалами.
5. Опиши, что осталось за рамками задачи.
```

## 5.5. Проектные и глобальные инструкции

Проектные правила полезны команде: они хранятся в репозитории и проходят ревью. Глобальные правила подходят для личных предпочтений, например отвечать на русском или объяснять сокращения.

Не помещайте личные предпочтения в общий `AGENTS.md`, если они не являются командной договорённостью. OpenCode поддерживает проектные и пользовательские инструкции; точные пути и порядок поиска проверяйте в актуальной документации. Для команды храните общие правила рядом с проектом.

## 5.6. Как проверить rules

**Тест 1 — терминология.** Попросите агента подготовить словарь терминов. Проверьте, не заменяет ли он названия сущностей произвольными синонимами.

**Тест 2 — неизвестные сведения.** Попросите написать требования, не сообщая новых данных о каналах и статусах. Проверьте, что неизвестное осталось открытым вопросом.

**Тест 3 — ограничения.** Попросите проанализировать документ и явно запретите менять файлы. Убедитесь, что агент не редактирует их.

Rules направляют поведение, но не дают математической гарантии. Важные ограничения подкрепляйте разрешениями инструмента, ревью и техническими проверками.

## 5.7. Практика

Создайте файл правил из Git Bash:

```bash
touch AGENTS.md
ls -l AGENTS.md
```

Откройте `AGENTS.md` в редакторе, которым пользуетесь, и вставьте пример из раздела 5.4. Не создавайте второй файл с похожим именем вроде `agents.md`: используйте точное имя `AGENTS.md`. После проверки:

```bash
git status --short
git diff -- AGENTS.md
cat AGENTS.md
```


1. Создайте `AGENTS.md`.
2. Попросите агента пересказать применяемые правила.
3. Выполните три теста выше.
4. Зафиксируйте запросы, ожидаемое и фактическое поведение в `docs/rules-test.md`.
5. При необходимости скорректируйте правила и проверьте `git diff`.

## Проверка результата

Есть компактный `AGENTS.md`, который содержит правила проекта, а не всю документацию. Правила проверены на практических запросах и не воспринимаются как замена техническим ограничениям.
