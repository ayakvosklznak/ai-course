**Время:** 60–75 минут.

## Глоссарий главы 6

- **Skill** — оформленная инструкция для повторяемого сценария работы агента.
- **`SKILL.md`** — файл, в котором описаны назначение, условия применения и шаги skill.
- **Frontmatter** — блок метаданных в начале Markdown-файла, обычно между строками `---`.
- **Сценарий** — последовательность шагов для достижения результата.
- **Критерий качества** — условие, по которому можно проверить результат работы skill.

## 6.1. Зачем выносить сценарий в skill

Предположим, вы регулярно уточняете требования. Каждый раз нужно определить цель, пользователей, границы, основной и альтернативные сценарии, ограничения, открытые вопросы и критерии приёмки. Это повторяемая процедура, которую удобно оформить как skill.

В OpenCode skills оформляются через `SKILL.md` в каталоге с именем сценария. Агент видит доступные skills и может загрузить нужную инструкцию, когда она подходит к задаче. Документация: https://opencode.ai/docs/skills/.

## 6.2. Skill, rules и prompt

- **Rules** задают постоянные рамки: как работать в проекте.
- **Prompt** описывает текущую задачу: что сделать сейчас.
- **Skill** задаёт процедуру: как выполнять класс задач.
- **Шаблон** задаёт форму результата: какие поля заполнить.

Например, rule запрещает выдумывать статусы заказа; skill проводит уточнение; prompt просит применить сценарий к уведомлениям; шаблон фиксирует требования с ID и критериями приёмки.

## 6.3. Структура skill

Для проектного skill используйте:

```text
.opencode/skills/grill-me/SKILL.md
```

В начале файла размещается YAML frontmatter с именем и описанием. Имя должно соответствовать имени каталога и требованиям OpenCode. Описание должно ясно объяснять, для каких задач сценарий предназначен.

## 6.4. Skill Grill Me

Создайте `.opencode/skills/grill-me/SKILL.md`:

```markdown
---
name: grill-me
description: Последовательно уточняет требования к новой функции, выявляет неизвестные сведения, ограничения, исключения и критерии приёмки
---

# Назначение
Помоги аналитику провести структурированное уточнение требований.
Не переходи сразу к написанию полной спецификации.

# Когда использовать
- Есть краткое описание новой функции.
- В постановке много неизвестного.
- Нужно подготовить вопросы заказчику или владельцу продукта.
- Нужно выявить альтернативные и ошибочные сценарии.

# Принципы
- Задавай вопросы по одному или небольшими логическими группами.
- Не спрашивай то, на что уже есть ответ в источниках.
- Не подменяй неизвестное собственными предположениями.
- Помечай ответ как факт, решение, предположение или вопрос.
- При противоречии сначала зафиксируй его.
- Не предлагай архитектуру до понимания ограничений.

# Порядок работы
1. Переформулируй цель и проверь понимание.
2. Определи пользователей и заинтересованные стороны.
3. Уточни границы функции.
4. Уточни основной сценарий.
5. Рассмотри альтернативные и ошибочные сценарии.
6. Выяви бизнес-правила и ограничения.
7. Уточни данные и внешние взаимодействия.
8. Уточни нефункциональные требования.
9. Сформируй критерии приёмки.
10. Составь список нерешённых вопросов.

# Формат результата
## Цель
## Подтверждённые сведения
## Принятые решения
## Предположения
## Открытые вопросы
## Сценарии
## Ограничения
## Черновые критерии приёмки

# Ограничения
- Не выдумывай ответы за заказчика.
- Не считай молчание подтверждением.
- Не записывай предположение в утверждённое требование.
- Не меняй проектные файлы без отдельного запроса.
```

## 6.5. Skill Requirements Review

Создайте `.opencode/skills/requirements-review/SKILL.md`:

```markdown
---
name: requirements-review
description: Проверяет требования на неоднозначность, неполноту, противоречия и тестируемость
---

# Назначение
Проведи независимое ревью требований. Найди проблемы и объясни их влияние,
но не переписывай документ целиком.

# Входные данные
Используй требования, связанные источники, AGENTS.md и шаблоны команды.
Если источников недостаточно, явно укажи это.

# Проверки
1. Однозначность: можно ли трактовать требование несколькими способами?
2. Полнота: отсутствуют ли важные условия и исключения?
3. Проверяемость: можно ли определить выполнение требования?
4. Согласованность: нет ли конфликтов?
5. Прослеживаемость: указан ли источник или основание?
6. Границы: понятно ли, что входит и не входит в объём?
7. Терминология: одинаково ли используются понятия?
8. Данные: определены ли входные и выходные данные?
9. Ошибки: рассмотрены ли негативные сценарии?
10. Нефункциональные свойства: рассмотрены ли безопасность,
    производительность, доступность и надёжность?

# Формат результата
Сгруппируй замечания:
- Критично: без исправления нельзя корректно реализовать или проверить.
- Существенно: вероятны разные трактовки или пропуск сценария.
- Рекомендация: улучшит читаемость или поддержку.

Для каждого замечания укажи ID/фрагмент, тип проблемы, последствие,
обоснование и вопрос или вариант исправления.

В конце укажи источники, непроверенные области и вывод о готовности.

# Ограничения
- Не выдумывай бизнес-правила.
- Не переписывай требования без запроса.
- Не называй замечание критичным без объяснения последствий.
- Не считай отсутствие информации доказательством отсутствия требования.
```

## 6.6. Дополнительные сценарии skills

Skills не обязаны закрывать всю профессию. Полезно иметь небольшой набор сценариев, которые запускаются по конкретному признаку. Ниже — три коротких разбора; полные файлы `SKILL.md` оформляются по образцу разделов 6.4–6.5.

### Project Discovery

- **Когда использовать:** незнакомый репозиторий, новая предметная область, много документов и противоречий.
- **Что делает:** исследует структуру, разделяет источники по типам, перечисляет противоречия и пробелы.
- **Ограничения:** не изменяет файлы и не делает выводов без источника.
- **Результат:** карта проекта, реестр источников и открытые вопросы. Подробнее — в главе 4.

### Edge Cases

- **Когда использовать:** требования или спецификация готовы, нужно найти граничные и ошибочные сценарии.
- **Что делает:** перебирает категории: пустые значения, повторы, запоздавшие события, недоступность, лимиты, отмена, конкурентные изменения.
- **Ограничения:** не придумывает правила; для каждого сценария указывает, какое правило нужно уточнить.
- **Результат:** список сценариев со статусом «описан / требует решения / вне объёма». Подробнее — в главе 9.

### ADR Draft

- **Когда использовать:** нужно решение по архитектуре, интеграции или способу реализации.
- **Что делает:** собирает контекст, варианты, критерии сравнения и последствия.
- **Ограничения:** не придумывает стоимость, SLA и оценки; помечает допущения; не принимает решение за команду.
- **Результат:** черновик ADR со статусом Proposed и списком вопросов к архитектору. Подробнее — в главе 10.

## 6.7. Как проверить skill

1. Убедитесь, что каталог и поле `name` совпадают.
2. Проверьте точное имя файла `SKILL.md`.
3. Обновите сессию OpenCode, если это требуется для обнаружения нового skill.
4. Попросите агента применить `grill-me` к задаче уведомлений.
5. Убедитесь, что он задаёт вопросы и не перескакивает сразу к спецификации.
6. Подготовьте черновик с намеренными пробелами и примените `requirements-review`.

Пример запроса, который вводится **в интерфейсе OpenCode**, а не в Git Bash:

> Примени skill `grill-me` к задаче уведомления пользователя при изменении статуса заказа. Сначала изучи документы. Задавай вопросы последовательно. Не составляй финальную спецификацию, пока не соберёшь ответы и не перечислишь открытые вопросы.

## 6.8. Улучшение и безопасность skills

Проверяйте сценарий на нескольких задачах: не повторяет ли он вопросы, не игнорирует ли источники, не делает ли предположений, не смешивает ли бизнес-требования с реализацией. Если skill слишком длинный, вынесите справочные материалы и шаблоны в отдельные файлы.

Не подключайте неизвестные skills без проверки. Изучите автора и источник, команды и скрипты, внешние адреса и передаваемые данные. Текст skill — инструкция для модели, но не автоматически доверенный код или безопасная процедура.

## 6.9. Практика

Подготовьте каталоги и файлы в Git Bash:

```bash
mkdir -p .opencode/skills/grill-me
mkdir -p .opencode/skills/requirements-review
touch .opencode/skills/grill-me/SKILL.md
touch .opencode/skills/requirements-review/SKILL.md
mkdir -p docs
touch docs/requirements-discovery.md docs/requirements-review.md
```

Вставьте содержимое skills из примеров выше. Проверьте точные пути и имена:

```bash
find .opencode/skills -type f -print
cat .opencode/skills/grill-me/SKILL.md
cat .opencode/skills/requirements-review/SKILL.md
git status --short
```

Если `find` не показывает `SKILL.md`, проверьте, что файл сохранён именно с таким расширением, а не как `SKILL.md.txt`.


1. Создайте оба skill.
2. Примените `grill-me` к исходной задаче.
3. Примените `grill-me` ко второй функции — например, к изменению адреса доставки — и сравните вопросы: учитывает ли skill контекст или повторяет один и тот же шаблон.
4. Сохраните результат в `docs/requirements-discovery.md`.
5. Подготовьте черновые требования.
6. Примените `requirements-review`.
7. Сохраните замечания в `docs/requirements-review.md`.
8. Исправьте только проблемы, для которых есть подтверждённая информация; остальные оставьте открытыми вопросами.
9. При желании оформите один дополнительный skill из раздела 6.6 и проверьте его на учебной задаче.

## Проверка результата

В репозитории есть два обнаруживаемых skill с разными задачами. Они имеют ясные описания, протестированы и не подменяют ответственность аналитика.
