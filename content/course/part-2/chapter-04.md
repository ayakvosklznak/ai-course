**Время:** 45–60 минут.

## Глоссарий главы 4

- **Контекст** — сведения, необходимые агенту для выполнения конкретной задачи.
- **Источник истины** — источник, которому доверяют для определённого типа сведений; он не обязательно один для всего проекта.
- **Реестр источников** — перечень документов и систем с указанием того, что они подтверждают и насколько актуальны.
- **Противоречие** — несовместимые утверждения в двух или более источниках.
- **Допущение** — временно принятое положение, которое ещё нужно подтвердить.
- **Прослеживаемость** — возможность пройти от вывода или требования к источнику, на котором оно основано.

## 4.1. Почему контекст — это не просто набор файлов

Представим, что агенту поручили подготовить спецификацию уведомлений о статусе заказа. В репозитории есть описание жизненного цикла заказа, API-контракт, схема базы данных, старые требования, ADR о выборе сервиса уведомлений и заметки со встреч.

Формально агент получил доступ к проекту. Но он ещё не знает, какие документы актуальны. Старый документ может говорить об email, актуальный API — поддерживать push, а заметки встречи — содержать вариант, который так и не был утверждён.

Если попросить агента «прочитать всё и написать требования», он может объединить историю, действующие правила и гипотезы в одну непротиворечивую на вид картину. Поэтому задача аналитика — помочь агенту разобраться в источниках.

## 4.2. Типы информации

| Категория | Пример | Как использовать |
|---|---|---|
| Подтверждённый факт | В API есть метод получения заказа | Использовать при наличии актуального источника |
| Действующее правило | Нельзя отправлять уведомление до подтверждения оплаты | Учитывать как ограничение |
| Принятое решение | Используется отдельный сервис уведомлений | Сверить с актуальным ADR и реализацией |
| Историческая информация | Ранее планировали использовать SMS | Не считать текущим решением |
| Предположение | Повторная отправка будет через очередь | Проверить у владельца решения |
| Открытый вопрос | Что делать при недоступности провайдера? | Зафиксировать и адресовать ответственному |

Это разделение помогает и модели, и аналитику видеть, где заканчиваются знания и начинаются предположения.

## 4.3. Источники истины и приоритеты

Нельзя универсально утверждать, что код всегда важнее документации или наоборот. Источник зависит от вопроса:
- фактическое поведение API может подтверждаться контрактом и реализацией;
- бизнес-ограничение — утверждённым продуктовыми владельцами правилом;
- архитектурный выбор — актуальным ADR;
- договорённости с внешней системой — контрактом поставщика.

Полезно завести `docs/source-register.md`:

```markdown
# Реестр источников

| Источник | Что подтверждает | Статус | Владелец/ответственный |
|---|---|---|---|
| API contract | Методы и форматы запросов | Требует проверки актуальности | Команда API |
| Order lifecycle | Допустимые переходы статусов | Учебный источник | Аналитик |
| ADR-001 | Архитектурное решение | Учебный источник | Архитектор |
| Meeting notes | Обсуждавшиеся варианты | Не является утверждением | Участники встречи |

## Правила использования
- Исторические заметки не считать утверждёнными требованиями.
- При конфликте источников фиксировать противоречие.
- Для существенных выводов указывать источник.
```

В реальном проекте добавляйте дату, версию, владельца и состояние документа.

## 4.4. Исследование незнакомого репозитория

Не начинайте с запроса «прочитай весь проект». Разбейте исследование на этапы.

**Этап 1. Обзор структуры.**

> Исследуй структуру текущего репозитория. Пока ничего не изменяй. Сгруппируй материалы по назначению: требования, архитектура, API, данные, тесты, эксплуатация и прочее. Не делай выводов о содержимом только по названиям файлов. Для важных файлов укажи путь и объясни, почему они могут быть полезны аналитику.

**Этап 2. Предметная область.**

> Найди материалы, описывающие жизненный цикл заказа и изменение его статуса. Сопоставь документы: укажи сведения, подтверждаемые несколькими источниками, сведения из одного источника и расхождения. Не исправляй документы.

**Этап 3. Карта проекта.** Создайте `docs/project-map.md`:

```markdown
# Карта проекта

## Назначение системы
...
## Основные компоненты
...
## Ключевые бизнес-сущности
...
## Интеграции
...
## Документы и источники
...
## Неизвестные области
...
## Противоречия и риски
...
```

Карта — навигационный документ, а не замена исходным материалам. Она должна ссылаться на них.

**Этап 4. Проверка.** Убедитесь, что каждый файл существует, подтверждает указанный тезис, а планируемые возможности не представлены как реализованные. Проверьте, что предположения и противоречия отмечены явно.

## 4.5. Работа с противоречиями

Допустим, `docs/order-lifecycle.md` говорит, что уведомление отправляется после каждого изменения статуса, а `docs/product-notes.md` — что сообщение отправляется только при значимых переходах.

Не просите модель выбрать «наиболее логичный» вариант. Логичность не заменяет согласование. Корректный результат анализа:

```markdown
## Противоречие: когда отправлять уведомление

Источник A: docs/order-lifecycle.md
- Указывает отправку после каждого изменения статуса.

Источник B: docs/product-notes.md
- Ограничивает уведомления значимыми статусами.

Влияние:
- Различается количество сообщений.
- Возможны лишние уведомления о внутренних переходах.

Что требуется уточнить:
- Какой документ отражает действующее продуктовое решение?
- Есть ли утверждённый перечень значимых статусов?
- Кто владелец решения?

Статус: не разрешено.
```

## 4.6. Как не перегружать контекст

- Сначала делайте обзор, затем изучайте релевантные файлы.
- Передавайте материалы, связанные с текущей задачей.
- Просите краткое резюме с путями к источникам.
- Не дублируйте большие документы в запросе, если агент может прочитать их сам.
- Разделяйте исследование, анализ и редактирование.
- Сохраняйте промежуточные выводы в репозитории.

## 4.7. Практика

Сначала подготовьте каталоги из Git Bash. Выполняйте команды из корня учебного проекта:

```bash
mkdir -p docs
touch docs/project-map.md docs/source-register.md
ls -la docs
```

После того как агент заполнит документы, проверьте изменения:

```bash
git status --short
git diff -- docs/project-map.md docs/source-register.md
```

Если файл новый и ещё не отслеживается Git, `git diff` может его не показать. В таком случае откройте файл редактором или выведите его содержимое:

```bash
cat docs/project-map.md
cat docs/source-register.md
```


1. Попросите агента исследовать структуру репозитория без изменений.
2. Создайте `docs/project-map.md` и `docs/source-register.md`.
3. Добавьте раздел «Неизвестные области».
4. Проверьте ссылки на файлы и `git diff`.

Если материалов мало, добавьте учебный `docs/order-lifecycle.md`:

```markdown
# Жизненный цикл заказа

Учебный документ.

Заказ создаётся после оформления покупки. После создания он проходит
несколько этапов обработки. Точный перечень статусов и допустимые
переходы в этом учебном проекте пока не определены.
```

И `docs/product-notes.md`:

```markdown
# Продуктовые заметки

Учебные заметки, не являющиеся утверждёнными требованиями.

Команда хочет информировать пользователя о важных изменениях заказа.
Перечень важных изменений пока не согласован. Каналы доставки требуют уточнения.
```

Попросите агента сравнить документы и перечислить вопросы, которые нельзя закрыть.

## Проверка результата

Глава выполнена, если создана карта проекта, есть реестр источников, факты отделены от предположений, противоречия не разрешаются догадкой, а выводы можно проверить по исходным файлам.
