# Паспорт курса

## Цель

Это не коллекция промптов и не обзор нейросетей. Курс учит строить повторяемый рабочий процесс, в котором ИИ помогает исследовать проект, уточнять требования, создавать и проверять документацию, сопоставлять источники и участвовать в командном процессе.

Ключевые принципы:
- контекст важнее эффектной формулировки запроса;
- подтверждённые факты нужно отделять от предположений;
- результаты должны быть проверяемыми и прослеживаемыми до источников;
- изменения файлов проверяются через Git;
- правила и повторяемые сценарии фиксируются в репозитории;
- ответственность за решения остаётся у специалиста и команды.

## Итоговые артефакты

К концу курса у слушателя будут карта проекта и список источников истины, `AGENTS.md`, набор рабочих skills, комплект требований и спецификация, ADR при необходимости, критерии приёмки, чек-листы качества и безопасности, а также описание процесса от исходного запроса до ревью.

## Предварительные знания

Нужны базовое понимание IT-проектов, умение читать Markdown и JSON и начальные знания Git. Глубокое программирование не требуется, но нужно быть готовым работать с терминалом и конфигурационными файлами.

## Windows и macOS

В Windows основная среда курса — **Git Bash**, который устанавливается вместе с Git for Windows. Это Bash-совместимая оболочка с командами `pwd`, `ls`, `cd`, `mkdir`, `cat` и привычным синтаксисом переменных окружения. В macOS отдельный Git Bash обычно не нужен: используйте встроенный Terminal с Zsh или Bash. Приведённые в учебнике команды будут Bash-командами и подойдут для обеих сред.

| Задача | Windows | macOS |
|---|---|---|
| Терминал курса | Git Bash | Terminal (Zsh/Bash) |
| Пример пути | `/c/Users/Username/ai-analyst-course` или `~/ai-analyst-course` | `~/ai-analyst-course` |
| Git | Git for Windows | Git из Command Line Tools или пакетного менеджера |
| Команды в учебнике | Bash | Bash-совместимый синтаксис |

**Важно:** не запускайте команды из учебника в PowerShell или `cmd.exe`, если отдельно не сказано обратное. В PowerShell другой синтаксис переменных и перенаправления. На macOS оболочка по умолчанию часто Zsh, но используемые здесь базовые команды Bash совместимы с Zsh.

## Сквозной проект

Мы будем работать с вымышленной системой обработки заказов интернет-магазина. Команда хочет уведомлять пользователя при изменении статуса заказа.

На первый взгляд задача простая, но нужно выяснить: какие статусы важны, какие каналы доступны, что делать при сбое доставки, как обрабатывать повторные события, как избежать дубликатов, какие данные можно передавать и где находится источник истины о статусе.

В учебных материалах все придуманные сведения должны быть явно отмечены как допущения, а не выдаваться за факты реальной системы.

# Глава 1. Как устроена работа аналитика с AI-агентом

**Время:** 60–75 минут.

## Глоссарий главы 1

- **LLM (Large Language Model):** большая языковая модель, которая обрабатывает контекст и генерирует ответы.
- **AI-агент:** приложение, которое использует модель и может выполнять действия через подключённые инструменты.
- **CLI:** интерфейс командной строки, в котором пользователь вводит команды текстом.
- **Терминал:** приложение, в котором запускается командная оболочка.
- **Оболочка (shell):** программа, интерпретирующая команды; в нашем курсе — Bash или совместимая с ним Zsh.
- **Git Bash:** Bash-совместимая оболочка, поставляемая с Git for Windows.
- **Репозиторий:** каталог проекта, состояние и история изменений которого отслеживаются Git.

## Цели главы

После главы вы сможете объяснить разницу между языковой моделью, чатом и агентом, понимать роль контекста, выбирать подходящие для ИИ задачи и проверять результат по источникам, а не по уверенности тона.

## 1.1. От разового запроса к процессу

Представим задачу: «Нужно уведомлять пользователя, когда меняется статус заказа. Подготовь требования для разработки».

Можно отправить её в чат с ИИ и получить список требований, критериев приёмки и обработки ошибок. Ответ может выглядеть профессионально, но модель не знает, какие статусы существуют в вашей системе, поддерживает ли продукт push-уведомления и какие правила повторной отправки уже приняты.

Она может предложить три повтора отправки или статус `SHIPPED`, хотя в реальном проекте такого правила или статуса нет. Это не обязательно ошибка формулировки запроса — просто модели не хватило контекста.

В этом курсе мы будем двигаться по циклу:

1. Найти исходные материалы.
2. Отделить подтверждённые факты от неизвестного.
3. Попросить ИИ помочь проанализировать сведения.
4. Сохранить результат в файлах проекта.
5. Проверить изменения.
6. Зафиксировать полезные правила и повторяемые сценарии.
7. Организовать ревью человеком.

ИИ ускоряет отдельные операции, но постановка задачи, оценка рисков и принятие решений остаются ответственностью специалиста.

## 1.2. Модель, чат и агент

**Языковая модель (LLM)** обрабатывает входной контекст и генерирует ответ. Она может помочь с формулировками, анализом, примерами SQL и поиском логических пробелов. Но если данных нет в контексте или доступных источниках, модель может ошибиться или представить предположение как факт.

**Чат** — интерфейс взаимодействия с моделью. Он удобен для обсуждения подходов, редактирования небольших фрагментов, объяснения терминов и первичного анализа идеи. Возможности чатов различаются: некоторые поддерживают поиск и работу с файлами, другие — нет.

**Агент** — приложение, которое использует модель и выполняет действия через доступные инструменты. Например, читает файлы, ищет текст, создаёт документы или запускает разрешённые команды. Набор действий зависит от инструмента, конфигурации и разрешений.

**CLI-агент** запускается из терминала. В этом курсе основным примером будет OpenCode. Его преимущество не в том, что он непременно «умнее чата», а в возможности работать рядом с материалами проекта и возвращать изменения, которые удобно проверять через Git.

## 1.3. Как агент получает контекст

Для анализа требований к уведомлениям могут понадобиться:
- исходная постановка;
- описание жизненного цикла заказа;
- API-контракт;
- модель данных;
- правила обработки ошибок;
- принятые архитектурные решения;
- шаблон требований команды.

Доступ к репозиторию не означает, что агент автоматически изучил всё его содержимое. В большом проекте могут быть тысячи файлов, устаревшие документы и противоречащие друг другу описания.

Поэтому полезно просить агента:
1. перечислить найденные источники;
2. отделить факты от гипотез;
3. указывать файлы и разделы, подтверждающие выводы;
4. перечислить вопросы, на которые нет ответа;
5. только затем предлагать изменения.

## 1.4. Уровни действий агента

| Действие | Пример | Что проверить |
|---|---|---|
| Прочитать | Изучить `docs/order-lifecycle.md` | Актуален ли источник |
| Найти | Найти упоминания статусов | Все ли нужные каталоги исследованы |
| Предложить | Выдать черновик в ответе | Какие сведения предположены |
| Создать файл | Добавить `docs/requirements.md` | Соответствует ли структуре проекта |
| Изменить файл | Дополнить спецификацию | Не потеряны ли договорённости |
| Выполнить команду | Запустить проверку | Безопасна ли команда |
| Изменить Git-состояние | Подготовить коммит | Что попадёт в коммит |

**Правило курса:** чем сильнее действие влияет на проект или внешнюю систему, тем яснее должны быть разрешения, подтверждение и способ отката.

## 1.5. Какие задачи подходят для ИИ

| Задача | Подходит? | Условия |
|---|---|---|
| Составить вопросы заказчику | Да | Не дублировать уже известные факты |
| Найти противоречия в документах | Да | Требовать ссылки на конкретные места |
| Подготовить критерии приёмки | Да | Сверить с требованиями и ограничениями |
| Подготовить структуру ADR | Да | Не выдумывать аргументы за команду |
| Утвердить архитектурное решение | Не делегировать целиком | ИИ может сравнить варианты, решение принимает команда |
| Опубликовать документ с персональными данными | Только в разрешённом процессе | Проверить политику данных и доступы |
| Выполнить разрушительную команду | Не без явного контроля | Понять последствия и возможность отката |

ИИ не обязательно должен выполнять задачу целиком. Часто достаточно получить черновик или список проблем, а затем проверить результат по чек-листу.

## 1.6. Почему красивый текст не равен качественному результату

Для аналитических артефактов важны:
1. **Прослеживаемость:** понятно, откуда взят каждый существенный факт.
2. **Явные допущения:** неизвестное не маскируется под требование.
3. **Проверяемость:** можно определить, выполнено ли требование.
4. **Согласованность:** документы не противоречат друг другу.
5. **Полнота в заданных границах:** рассмотрены существенные сценарии.
6. **Поддерживаемость:** коллега может продолжить работу без пересказа чата.

Объём, таблицы и профессиональная терминология сами по себе не подтверждают качество.

## 1.7. Установка Git for Windows и знакомство с Git Bash

В этом курсе мы будем выполнять команды через Git Bash. Это позволит использовать единый синтаксис для навигации по каталогам, работы с файлами, Git и запуска OpenCode. На macOS используйте обычный Terminal: команды в учебнике совместимы с Bash и Zsh.

### Шаг 1. Скачать Git for Windows

1. Откройте официальный сайт: https://git-scm.com/install/windows.
2. Скачайте установщик для архитектуры своего компьютера (обычно x64).
3. Запустите установщик. Используйте настройки по умолчанию, если не уверены, что менять.
4. На шаге выбора редактора можно оставить предложенный вариант или выбрать установленный редактор. Это не влияет на выполнение команд курса.
5. На шаге настройки PATH оставьте вариант, позволяющий запускать Git из командной строки и сторонних программ (обычно рекомендованный вариант).
6. В качестве терминального приложения для Git выберите MinTTY или Windows Console Host — оба подходят. Для курса запускайте именно Git Bash из меню «Пуск».
7. Завершите установку.

Официальный сайт Git for Windows также описывает Git Bash как Bash-эмуляцию для запуска Git и Unix-подобных команд в Windows: https://gitforwindows.org/.

### Шаг 2. Открыть Git Bash

Нажмите «Пуск», введите `Git Bash` и запустите приложение. Откроется окно терминала с приглашением командной строки. Можно также открыть папку проекта в Проводнике, нажать правой кнопкой мыши и выбрать `Open Git Bash here`, если такой пункт доступен.

### Шаг 3. Проверить установку

Введите по очереди:

```bash
git --version
bash --version
pwd
```

Ожидаемый результат: первые две команды выводят версии Git и Bash, третья показывает текущий каталог. Номер версии может отличаться — это нормально.

### Шаг 4. Настроить имя и email для Git

Укажите имя и email, которые должны отображаться в истории коммитов. Для учебного репозитория можно использовать учебные значения; для рабочего проекта следуйте правилам команды.

```bash
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
git config --global --list
```

Замените `Your Name` и `you@example.com` на свои значения. Email в коммитах может быть виден другим участникам репозитория. Если не хотите публиковать личный адрес, используйте настроенный privacy-email вашего Git-хостинга.

### Шаг 5. Создать рабочую папку курса

В Git Bash домашний каталог пользователя доступен через `~`. Выполните:

```bash
mkdir -p ~/ai-analyst-course/docs
cd ~/ai-analyst-course
pwd
```

Команда `pwd` должна показать путь, заканчивающийся на `ai-analyst-course`. Путь `/c/Users/...` — нормальное представление диска `C:` в Git Bash. Не пытайтесь вручную заменять его на `C:\...` в Bash-командах.

### Шаг 6. Базовые команды Bash, которые понадобятся в курсе

| Команда | Назначение | Пример |
|---|---|---|
| `pwd` | Показать текущий каталог | `pwd` |
| `ls` | Показать файлы и папки | `ls -la` |
| `cd` | Перейти в каталог | `cd ~/ai-analyst-course` |
| `mkdir -p` | Создать каталог вместе с родительскими | `mkdir -p docs/specs` |
| `cat` | Вывести содержимое файла | `cat notes.md` |
| `touch` | Создать пустой файл | `touch notes.md` |
| `cp` | Скопировать файл | `cp a.md a-backup.md` |
| `mv` | Переместить или переименовать | `mv draft.md final.md` |
| `rm` | Удалить файл | `rm temporary.txt` |

С командой `rm` будьте внимательны: удалённый таким способом файл может не попасть в корзину. Не используйте `rm -rf`, пока не понимаете, какой именно каталог будет удалён.

Откройте приложение Terminal. Проверьте оболочку и Git:

## 1.9. Самопроверка

Агент написал: «Уведомление отправляется по email сразу после перехода заказа в статус `SHIPPED`. При ошибке система повторяет отправку три раза».

Что проверить?
- Существует ли `SHIPPED` в модели статусов?
- Действительно ли используется email?
- Что означает «сразу» и как это измеряется?
- Предусмотрены ли повторы и почему выбрано именно три?
- Может ли повтор привести к дубликату?
- Есть ли источник, подтверждающий эти правила?

## Выводы главы

- Агент отличается от обычного чата возможностью работать через инструменты.
- Контекст нужно организовывать, а не просто «давать модели побольше текста».
- Неизвестные требования нельзя автоматически превращать в факты.
- Качество определяется прослеживаемостью, проверяемостью и согласованностью.
- Ответственность за решения остаётся у человека и команды.

# Глава 2. Установка и настройка OpenCode

**Время:** 90–120 минут.

## Глоссарий главы 2

- **OpenCode:** AI-агент, который запускается в терминале и может анализировать файлы проекта, отвечать на вопросы и выполнять разрешённые действия.
- **CLI (Command-Line Interface):** интерфейс командной строки; OpenCode запускается из него командой `opencode`.
- **TUI (Text User Interface):** текстовый интерфейс OpenCode внутри терминала. Это не обычная строка Bash: команды OpenCode и команды Bash вводятся в разных местах.
- **Провайдер (provider):** сервис или локальная инфраструктура, через которую OpenCode обращается к языковой модели.
- **API:** программный интерфейс, через который приложения отправляют запросы и получают ответы.
- **API-ключ:** секретный токен для доступа к API провайдера. По смыслу похож на пароль, поэтому его нельзя публиковать или добавлять в Git.
- **Модель:** конкретная языковая модель, которую предоставляет выбранный провайдер.
- **Локальная модель:** модель, которая работает на вашем компьютере или сервере, а не в облаке провайдера.
- **Разрешения агента:** правила, определяющие, какие действия агент выполняет сам, а какие требуют подтверждения.
- **OAuth:** способ авторизации через вход в аккаунт и подтверждение доступа, без ручного копирования API-ключа.
- **`PATH`:** список каталогов, в которых терминал ищет исполняемые программы.
- **npm:** менеджер пакетов Node.js. В этой главе он используется для установки OpenCode CLI.

> **Версия и актуальность.** В этой главе используется OpenCode 2 (V2) и пакет `@opencode/cli`. У OpenCode 1 и OpenCode 2 одинаковая команда запуска `opencode`, но разные пакеты установки. Не устанавливайте их одновременно: они могут конфликтовать. Команды и интерфейс могут меняться; перед установкой сверяйтесь с [официальной инструкцией OpenCode V2](https://opencode.ai/v2/docs) и [документацией по провайдерам](https://dev.opencode.ai/v2/docs/cli/providers).

## 2.1. Что мы установим и какой результат должен получиться

В этой главе настроим рабочую связку:

1. Git Bash в Windows или Terminal в macOS — оболочка, в которой выполняются команды.
2. Node.js и npm — среда выполнения и менеджер пакетов.
3. OpenCode CLI V2 — агент, который запускается командой `opencode`.
4. Провайдер и модель — сервис и конкретная LLM, к которой агент будет обращаться.
5. Учебный каталог — безопасное место для первых экспериментов.
6. Разрешения — ограничения на чтение, запись и выполнение команд.

К концу главы вы сможете открыть Git Bash, перейти в папку учебного проекта, запустить OpenCode, подключить провайдера, выбрать модель и получить ответ на тестовый запрос, а также поймёте, как подключить локальную модель и как разрешения ограничивают действия агента.

**Важно различать:** OpenCode — это не сама языковая модель и не поставщик вычислений. Установка OpenCode не означает, что у вас автоматически появился бесплатный доступ к любой модели. Для работы нужен отдельный способ авторизации у выбранного провайдера: API-ключ, OAuth или другой поддерживаемый способ.

## 2.2. Перед установкой: что должно быть готово

Проверьте, что:

- Git Bash установлен в Windows по пункту 1.7 (на macOS используйте Terminal);
- терминал открывается и команды `pwd`, `ls` и `git --version` работают;
- есть доступ к интернету;
- вы можете устанавливать программы на своём компьютере;
- вы выбрали провайдера, который разрешено использовать для учебных данных.

Если вы работаете на корпоративном компьютере, сначала проверьте внутренние правила. Не отправляйте в сторонний сервис реальные персональные данные, коммерческую тайну, внутренние документы или исходный код, если это не разрешено организацией.

### API-доступ и подписка на чат — не одно и то же

Подписка на веб-чат конкретного сервиса не всегда включает API-доступ. API может оплачиваться отдельно, по фактическому использованию или по собственному тарифу провайдера. У некоторых провайдеров OpenCode поддерживает вход через аккаунт/OAuth, поэтому API-ключ вручную создавать не требуется. Условия зависят от конкретной интеграции.

Перед подключением проверьте на сайте провайдера:

- доступен ли сервис в вашей стране;
- какие модели доступны вашему аккаунту;
- требуется ли включить биллинг или пополнить баланс;
- какие действуют лимиты и тарифы;
- как провайдер обрабатывает и хранит отправляемые данные.

Для первых упражнений используйте только учебные, вымышленные данные курса.

## 2.3. Проверяем Git Bash и устанавливаем Node.js

OpenCode V2 можно установить разными способами. В нашем курсе используем npm: это понятный и воспроизводимый путь для Windows с Git Bash и для macOS.

### Шаг 1. Откройте правильный терминал

**Windows:** откройте меню «Пуск», найдите `Git Bash` и запустите его.

**macOS:** откройте приложение `Terminal`.

Далее все команды из блоков с пометкой «Терминал» вводятся именно в этом окне. Не вводите их в интерфейс OpenCode, пока он запущен: это разные среды.

### Шаг 2. Проверьте Git и оболочку

Введите:

```bash
git --version
printf 'Shell: %s\n' "$SHELL"
pwd
```

Первая команда должна вывести версию Git, последняя — текущую папку. Значение `SHELL` может отличаться в зависимости от системы; для курса важно, что вы работаете в Git Bash или Bash-совместимом Terminal.

### Шаг 3. Установите Node.js

Откройте официальный сайт Node.js: https://nodejs.org/ . Скачайте актуальную LTS-версию для своей операционной системы.

**Windows:**

1. На сайте Node.js выберите Windows Installer для своей архитектуры (для большинства современных компьютеров — x64).
2. Запустите скачанный `.msi`-файл.
3. В мастере установки оставьте стандартные параметры. В частности, не отключайте добавление Node.js в `PATH`.
4. Завершите установку.
5. Закройте все окна Git Bash и откройте Git Bash заново, чтобы он получил обновлённый `PATH`.

**macOS:**

1. На сайте Node.js выберите установщик для macOS и своей архитектуры (Apple Silicon или Intel).
2. Откройте `.pkg` и пройдите мастер установки.
3. Закройте и снова откройте Terminal.

Если Node.js уже установлен через менеджер версий (например, nvm), не устанавливайте поверх него второй независимый способ без необходимости. Важно, чтобы `node` и `npm` были доступны в том терминале, из которого вы будете запускать OpenCode.

### Шаг 4. Проверьте Node.js и npm

В Git Bash или Terminal выполните:

```bash
node --version
npm --version
```

Обе команды должны вывести номера версий. Например, результат может выглядеть как `vXX.YY.Z` и `XX.YY.Z`; конкретные цифры будут зависеть от установленной версии.

Если терминал сообщает `command not found` или `not recognized`:

1. убедитесь, что установка завершилась без ошибок;
2. полностью закройте терминал и откройте заново;
3. повторите команды проверки;
4. если проблема осталась, проверьте установку Node.js и переменную `PATH` по документации Node.js для вашей ОС.

Не копируйте случайные команды исправления `PATH` из форумов: неправильное изменение системных путей может нарушить работу других инструментов.

## 2.4. Устанавливаем OpenCode V2

### Важное различие между V1 и V2

В документации OpenCode существуют две ветки:

| Ветка | npm-пакет | Команда запуска |
|---|---|---|
| OpenCode 1 | `opencode-ai` | `opencode` |
| OpenCode 2 | `@opencode/cli` | `opencode` |

В этом курсе используем **OpenCode 2**. Поэтому устанавливаем именно `@opencode/cli`. Не запускайте команду установки `npm install -g opencode-ai`, если следуете этой версии учебника: это пакет OpenCode 1.

### Шаг 1. Установка через npm

В обычной строке Git Bash / Terminal (не внутри OpenCode) выполните:

```bash
npm install -g @opencode/cli
```

Дождитесь окончания установки. npm загрузит пакет и установит подходящий исполняемый файл для вашей платформы.

### Шаг 2. Проверка установки

Выполните:

```bash
opencode --version
```

Если команда вывела номер версии OpenCode 2, установка прошла успешно.

Дополнительно можно проверить, откуда терминал запускает программу:

```bash
command -v opencode
```

Команда должна вывести путь к исполняемому файлу или npm shim. Необязательно запоминать этот путь; проверка нужна, чтобы убедиться, что терминал находит OpenCode.

### Если команда `opencode` не найдена

1. Закройте Git Bash / Terminal и откройте заново.
2. Проверьте, что npm действительно завершил установку без ошибок:

   ```bash
   npm list -g --depth=0
   ```

3. Проверьте глобальный префикс npm:

   ```bash
   npm config get prefix
   ```

4. Посмотрите, видит ли оболочка команду:

   ```bash
   command -v opencode
   ```

5. Если пакет установлен, но команда не находится, вероятно, каталог глобальных исполняемых файлов npm не добавлен в `PATH`. Не угадывайте путь вручную: он зависит от способа установки Node.js и операционной системы. Сверьтесь с официальной документацией npm для вашей конфигурации или используйте установщик Node.js, который корректно добавляет npm в `PATH`.

Если на компьютере ранее был установлен OpenCode 1, не устанавливайте V2 поверх него наугад. Сначала выясните, какой пакет установлен, удалите конфликтующую версию штатным способом и затем установите выбранную ветку. Помните: у обеих веток одна команда `opencode`, поэтому сам факт запуска команды не доказывает, что установлена нужная версия. Проверяйте `opencode --version` и список глобальных пакетов npm.

## 2.5. Первый запуск и знакомство с интерфейсом

### Шаг 1. Перейдите в учебный каталог

Если вы выполняли команды из главы 1, каталог уже создан:

```bash
cd ~/ai-analyst-course
pwd
ls -la
```

`pwd` должен показать путь к `ai-analyst-course`. Если папки пока нет, создайте её:

```bash
mkdir -p ~/ai-analyst-course/docs
cd ~/ai-analyst-course
```

### Шаг 2. Запустите OpenCode

```bash
opencode
```

Откроется TUI — текстовый интерфейс агента прямо в терминале. Теперь вы находитесь не в обычной строке Bash, а внутри OpenCode.

В нижней части интерфейса обычно находится поле ввода сообщения. Напишите короткий запрос, например:

```text
Привет. Кратко объясни, какие задачи ты можешь выполнять в рамках открытого проекта. Пока ничего не изменяй.
```

Отправьте сообщение клавишей Enter. На этом этапе ответ может не прийти, если ещё не настроен провайдер. Это ожидаемо: сначала подключим модель.

### Как вернуться из OpenCode в Git Bash

Для выхода из TUI используйте команду `/exit`, если она поддерживается текущей сборкой, или клавишу `Ctrl+C`. После выхода вы снова увидите обычное приглашение Git Bash / Terminal и сможете вводить команды вроде `pwd`, `ls` и `npm`.

**Не путайте два типа команд:**

- `cd`, `ls`, `npm install` — команды оболочки, вводятся в Git Bash / Terminal;
- `/connect`, `/models`, `/exit` — команды интерфейса OpenCode, вводятся внутри TUI.

## 2.6. Подключаем провайдера и авторизуемся

Есть два распространённых варианта авторизации:

1. **API-ключ:** вы создаёте секретный ключ в кабинете провайдера и вводите его в OpenCode.
2. **OAuth / вход через аккаунт:** OpenCode открывает страницу авторизации или показывает код, а вы подтверждаете доступ в браузере.

Какой вариант доступен, зависит от выбранного провайдера. Не все провайдеры поддерживают оба способа.

### Шаг 1. Откройте список провайдеров

Если OpenCode ещё не запущен, выполните в Git Bash:

```bash
cd ~/ai-analyst-course
opencode
```

Когда появится интерфейс OpenCode, введите в поле сообщения:

```text
/connect
```

Нажмите Enter. OpenCode покажет список интеграций, доступных в текущей версии.

### Шаг 2. Выберите провайдера

Перемещайтесь по списку клавишами, которые показывает интерфейс, и выберите нужный сервис. Например, это может быть OpenAI, Anthropic, OpenRouter или OpenCode Console — точный список зависит от версии и доступности интеграций.

Если провайдер предлагает несколько способов входа, выберите подходящий:

- `API key` / `Enter API key` — ввод ключа;
- `OAuth` / `Sign in` — авторизация через браузер;
- другой метод — только если вы понимаете, как он работает и он разрешён вашей организацией.

### Шаг 3А. Если выбран API-ключ: где его получить

API-ключ создаётся на официальном сайте провайдера, а не в OpenCode. Общая последовательность такая:

1. Откройте официальный сайт выбранного провайдера.
2. Войдите в аккаунт.
3. Найдите раздел для разработчиков или API. Он может называться `API keys`, `Developer`, `Credentials` или `API settings`.
4. Если провайдер требует, включите API billing / оплату API и ознакомьтесь с лимитами.
5. Нажмите кнопку создания ключа — например, `Create API key`, `New secret key` или аналогичную.
6. Если можно задать название, назовите ключ понятно, например `opencode-course-laptop`.
7. Скопируйте созданный ключ и временно держите его только в буфере обмена.

Ключ часто показывается полностью только один раз. Если вы закрыли страницу и потеряли его, обычно нужно создать новый. Не пытайтесь восстановить старый ключ через историю браузера или отправлять его себе в мессенджер.

**Не существует одного универсального API-ключа для всех моделей.** Ключ OpenAI не является ключом Anthropic, а ключ OpenRouter не является ключом OpenAI. Создавайте ключ именно у того провайдера, которого выбрали в `/connect`.

### Шаг 3Б. Если выбран API-ключ: куда его вставить

Вернитесь в окно Git Bash, где открыт OpenCode. После выбора провайдера появится поле или приглашение для ввода API key.

1. Убедитесь, что в OpenCode выбран правильный провайдер.
2. Вставьте ключ в поле, которое показывает сам OpenCode.
3. Подтвердите ввод клавишей Enter.
4. Дождитесь сообщения об успешной авторизации или возвращения к списку провайдеров.

В Git Bash вставка из буфера обмена обычно выполняется правой кнопкой мыши или сочетанием `Shift+Insert`; сочетание `Ctrl+Shift+V` также может работать в зависимости от настроек терминала. Если вставка не срабатывает, используйте контекстное меню терминала.

Во время ввода секрет может отображаться не полностью или не отображаться вовсе. Это нормально. Не вставляйте ключ в обычную строку Bash и не отправляйте его сообщением в чат OpenCode.

### Шаг 3В. Если выбран OAuth / вход через аккаунт

Если вместо поля API key OpenCode предлагает открыть браузер или ввести код:

1. Следуйте инструкции, которую показывает OpenCode.
2. Если показана ссылка, откройте её в браузере. В некоторых интерфейсах клавиша `o` открывает ссылку, а `c` копирует данные авторизации — ориентируйтесь на подсказки конкретного экрана.
3. Войдите в аккаунт провайдера и внимательно прочитайте, какие права запрашиваются.
4. Подтвердите доступ, если согласны.
5. Вернитесь в терминал и дождитесь завершения авторизации.

При OAuth вы можете не увидеть и не вводить API-ключ вручную: это нормальный сценарий. OpenCode сохранит необходимые токены авторизации.

### Шаг 4. Убедитесь, что авторизация сохранена

Выйдите из TUI командой `/exit` или `Ctrl+C`, затем в Git Bash выполните:

```bash
opencode auth list
```

Команда показывает настроенные способы авторизации и сохранённые аккаунты. Она не должна выводить секретный ключ целиком. Если список пуст, подключение не завершено — повторите `/connect` и проверьте выбранный способ авторизации.

## 2.7. Выбираем модель

Авторизация провайдера ещё не всегда означает, что конкретная модель выбрана. Нужно выбрать модель, доступную вашему аккаунту.

### Шаг 1. Запустите OpenCode

```bash
cd ~/ai-analyst-course
opencode
```

### Шаг 2. Откройте список моделей

Внутри TUI введите:

```text
/models
```

Откроется список моделей. Выберите ту, которая доступна через подключённого провайдера. В некоторых версиях интерфейс позволяет искать модель по названию.

### Какую модель выбрать для обучения

Для учебных задач аналитика полезна модель, которая:

- уверенно работает с длинными текстами и несколькими файлами;
- аккуратно извлекает факты и не смешивает их с предположениями;
- умеет следовать заданной структуре ответа;
- хорошо справляется с анализом требований и поиском противоречий;
- имеет приемлемую стоимость и скорость;
- допускает обработку тех данных, с которыми вы собираетесь работать.

Не нужно выбирать самую дорогую модель для каждого запроса. В дальнейшем мы научимся подбирать модель под задачу и проверять качество на одном и том же наборе материалов.

### Локальная модель

Если данные нельзя отправлять в облако или нужна автономная среда, можно подключить локальную модель. Обычно локальная среда выполнения предоставляет API, совместимый с OpenAI, и OpenCode обращается к ней как к провайдеру. Точные шаги зависят от среды и версии OpenCode: сверяйтесь с официальной документацией.

Перед выбором проверьте:

- хватает ли памяти и вычислительных ресурсов;
- поддерживает ли модель нужный размер контекста и вызов инструментов;
- какова скорость ответа;
- где хранятся логи и кэш;
- как обновляется модель.

Локальная модель не обязательно даёт качество облачной на сложных аналитических задачах. Проверьте её на тех же контрольных запросах: чтение файлов, выделение фактов, следование структуре. Для первых упражнений достаточно облачной модели; локальную подключайте, когда есть понятное ограничение по данным.

## 2.8. Проверяем подключение на простом запросе

Оставаясь внутри OpenCode, отправьте запрос:

```text
Ответь одной короткой фразой: «Подключение работает». Не выполняй команды и не изменяй файлы.
```

Если вы получили ответ, базовая связка «OpenCode — провайдер — модель» работает.

Затем можно задать контрольный вопрос:

```text
Кратко назови модель и провайдера, которые доступны в текущей сессии. Если ты не можешь достоверно определить эти сведения, так и скажи — не угадывай.
```

## 2.10. Настройки, разрешения и секреты

OpenCode хранит авторизационные данные отдельно от файлов проекта. В OpenCode V2 сохранённые API-ключи и OAuth-токены хранятся в локальной базе данных SQLite в каталоге данных пользователя. Точный путь можно посмотреть командой:

```bash
opencode debug paths db
```

Не редактируйте эту базу вручную и не пытайтесь добавлять её в репозиторий. Для управления подключениями используйте `/connect` в TUI или команды `opencode auth`.

Разделяйте три категории информации:

| Категория | Примеры | Где хранить |
|---|---|---|
| Общие инструкции проекта | `AGENTS.md`, правила оформления, соглашения команды | В репозитории, если они предназначены для команды |
| Личные настройки | Предпочтения интерфейса, локальные параметры | В пользовательской конфигурации |
| Секреты | API-ключи, OAuth-токены, пароли | В защищённом хранилище авторизации или менеджере секретов |

**Никогда не делайте следующее:**

- не вставляйте API-ключ в промпт;
- не записывайте его в `AGENTS.md`, Markdown-файл или `opencode.json`;
- не добавляйте базу авторизации OpenCode в Git;
- не помещайте ключ в команду вида `opencode --key ...` или в историю терминала;
- не отправляйте секреты в мессенджер и не публикуйте скриншоты, где они могут быть видны;
- не используйте рабочий ключ компании для личных экспериментов без разрешения.

**Переменные окружения.** Ключ можно передать через переменную окружения, чтобы не хранить его в файле проекта. Но не записывайте значение в `.env`, который попадает в Git, не выводите переменную в терминал и проверьте, что `.env` исключён в `.gitignore`. Переменная окружения не делает ключ безопасным сама по себе: она лишь уменьшает риск случайной публикации.

Если ключ случайно попал в репозиторий или был опубликован, считайте его скомпрометированным: отзовите его в кабинете провайдера, создайте новый и проверьте историю Git. Простое удаление строки из последнего коммита не гарантирует, что секрет исчез из истории.

### Разрешения на действия агента

Правила в `AGENTS.md` направляют поведение, но не блокируют действия технически. Отдельно настраиваются разрешения: что агент может читать, изменять и выполнять.

| Действие | Риск | Рекомендация для обучения |
|---|---|---|
| Чтение файлов проекта | Доступ к лишним данным | Разрешить в пределах каталога проекта |
| Создание и изменение файлов | Потеря изменений | Спрашивать подтверждение или проверять diff |
| Выполнение команд | Разрушительные операции | Спрашивать подтверждение |
| Сетевые запросы | Передача данных | Ограничить или спрашивать |
| Внешние действия | Изменение внешних систем | Запретить до отдельной задачи |

Начните с режима, в котором запись и выполнение команд требуют подтверждения. Разрешайте автоматические действия только после того, как убедились в их безопасности на учебном проекте.

Точные названия режимов и способ настройки зависят от версии OpenCode. Сверяйтесь с официальной документацией и не копируйте конфигурацию из случайных источников. Технические разрешения важнее текстовых правил: правило «не изменяй файлы» не остановит агента, если запись разрешена.

## 2.11. Частые проблемы и способы диагностики

| Симптом | Что проверить и сделать |
|---|---|
| `node: command not found` | Node.js не установлен или не попал в `PATH`. Проверьте установку, перезапустите терминал и повторите `node --version`. |
| `npm: command not found` | Проверьте установку Node.js/npm и `PATH`. |
| `opencode: command not found` | Проверьте `npm list -g --depth=0`, затем `npm config get prefix`; перезапустите терминал. |
| Установилась не та версия | Проверьте `opencode --version` и глобальные пакеты npm. Для курса нужен V2 и пакет `@opencode/cli`. |
| `/connect` не показывает нужного провайдера | Проверьте версию OpenCode, доступность интеграции и официальную документацию провайдера. |
| API-ключ отклонён | Проверьте, что ключ создан именно у выбранного провайдера, не отозван, скопирован целиком и API-доступ включён. |
| Ошибка оплаты или лимита | Проверьте баланс, биллинг, лимиты и тариф API в кабинете провайдера. |
| OAuth не завершается | Убедитесь, что браузер открыл правильную ссылку, вы вошли в нужный аккаунт и подтвердили доступ. Проверьте, не истёк ли код авторизации. |
| Модель отсутствует в `/models` | Возможно, модель не поддерживается провайдером или недоступна вашему аккаунту. Проверьте список моделей у провайдера. |
| Ошибка сети | Проверьте интернет, VPN, прокси, DNS и корпоративные сетевые ограничения. |
| Агент не видит файл | Выполните в Git Bash `pwd`, проверьте путь и запускайте `opencode` из корня проекта. |
| Ответ слишком дорогой | Проверьте тариф, выбранную модель, объём контекста и частоту запросов. |

Если ошибка сохраняется, зафиксируйте её текст, версию OpenCode и провайдера. Перед отправкой лога в публичный форум удалите из него ключи, токены, адреса внутренних сервисов и другие чувствительные данные.

# Глава 3. Git и безопасная работа с файлами

**Время:** 45–60 минут.

## Глоссарий главы 3

- **Git:** система контроля версий, которая хранит историю изменений файлов.
- **Рабочий каталог (working tree):** текущие файлы проекта на диске.
- **Индекс (staging area):** область, куда подготавливают изменения для следующего коммита.
- **Коммит (commit):** зафиксированный набор изменений в истории Git.
- **Diff:** представление различий между версиями файлов.
- **`git restore`:** команда, возвращающая файлы к состоянию из индекса.
- **Откат (rollback):** возврат к предыдущему состоянию файлов или коммитов.
- **`.gitignore`:** файл с правилами, какие неотслеживаемые файлы Git должен игнорировать.
- **Ветка (branch):** отдельная линия истории изменений.

## 3.1. Зачем аналитику Git

Агент может затронуть больше файлов, чем ожидалось, переписать соседние разделы или «исправить» утверждённый термин. Git позволяет увидеть изменения и вернуться к предыдущему состоянию.

Рабочий цикл:
1. Проверить исходное состояние.
2. Поставить агенту ограниченную задачу.
3. Изучить изменённые файлы.
4. Проверить diff.
5. Запустить доступные проверки.
6. Принять, доработать или откатить изменения.
7. Создать коммит после проверки.

Не коммитьте результат только потому, что агент сообщил об успехе.

## 3.2. Инициализация

Выполняйте команды из каталога `~/ai-analyst-course` в Git Bash (Windows) или Terminal (macOS). Весь синтаксис ниже — Bash.

```bash
git init
git status
git --version
```

Если Git отсутствует, установите его по официальной документации для своей ОС. В Windows используйте Git Bash, установленный в главе 1.

## 3.3. Файл `.gitignore`

Начальный вариант:

```gitignore
# Локальные секреты и переменные окружения
.env
.env.*
!.env.example

# Временные файлы ОС и редакторов
.DS_Store
Thumbs.db
*.swp
```

Это не универсальный шаблон: состав зависит от проекта. `.gitignore` не удаляет файлы, которые Git уже отслеживает, и не защищает секрет, ранее попавший в историю.

## 3.4. Проверка изменений

```bash
git status
git diff
git diff --stat
git diff --staged
```

- `git status` показывает состояние файлов.
- `git diff` показывает изменения, ещё не добавленные в индекс.
- `git diff --stat` даёт краткую сводку.
- `git diff --staged` показывает то, что подготовлено к коммиту.

В diff проверяйте:
- не исчезли ли существующие требования;
- не заменены ли утверждённые термины;
- не появились ли неподтверждённые сроки, статусы или значения;
- не сломались ли ссылки;
- не попали ли секреты или персональные данные;
- не затронуты ли посторонние файлы.

## 3.5. Первый коммит

Добавляйте файлы явно. Например:

```bash
git add docs/initial-request.md docs/environment-notes.md
git diff --staged
git commit -m "Add initial course materials"
```

Выполняйте `git add` только для существующих файлов, которые действительно хотите включить. Перед коммитом проверьте staged diff.

Если Git просит указать имя и email автора, используйте значения, подходящие для учебной или рабочей среды.

## 3.6. Откат изменений

Универсальной безопасной команды отката нет. Сначала определите, что именно нужно отменить: изменения в рабочем каталоге, в индексе или уже созданный коммит.

Команды, принудительно заменяющие локальные файлы содержимым из Git, могут уничтожить незакоммиченные изменения. Не запускайте их вслепую. Если сомневаетесь, сначала сохраните копию или создайте отдельную ветку.

Если предстоит рискованный эксперимент, создайте отдельную ветку:

```bash
git switch -c experiment
```

После проверки вернитесь в основную ветку командой `git switch -` или укажите её имя явно. Ветка сохраняет эксперимент, не затрагивая основную историю; удалять её сразу не обязательно.

## 3.7. Как ставить задачи агенту

**Слишком общий запрос:**

Непонятно, какие файлы разрешено менять и что считать результатом.

**Более управляемый запрос:**

Не добавляй сведения о статусах, каналах уведомления или повторной отправке, если их нет в источнике. После создания перечисли изменённые файлы. Не выполняй команды Git и не создавай коммит.

Здесь заданы область работы, структура результата и ограничения. Проверка всё равно нужна, но становится проще.

### Сценарий: нежелательные изменения и откат

Убедитесь, что текущее состояние закоммичено (или отмените изменения шага 8): сценарий должен начинаться с чистого рабочего каталога. Затем попросите агента изменить два документа:

> Прочитай `docs/initial-request.md` и `docs/environment-notes.md`. Улучши формулировки и добавь в каждый файл раздел «Допущения». Изменяй только эти два файла. Не выполняй команды Git.

После ответа проверьте, что именно изменилось:

```bash
git status --short
git diff --stat
git diff -- docs/initial-request.md docs/environment-notes.md
```

Найдите хотя бы одно нежелательное изменение: удалённое неизвестное, придуманное требование или правку в другом файле. Отмените изменения в одном файле:

```bash
git restore docs/initial-request.md
```

Затем отмените остальные незакоммиченные изменения в отслеживаемых файлах:

```bash
git restore .
git status --short
git diff
```

`git restore` возвращает файлы к состоянию из индекса. Он не отменяет уже созданные коммиты и не удаляет новые неотслеживаемые файлы — их нужно удалять отдельно и осознанно. Для отмены коммита используйте `git revert`, а не `git reset --hard`: `reset` может уничтожить работу без возможности восстановления.

**Дополнительное задание:** попросите агента предложить дополнение к `docs/initial-request.md`, но не разрешайте ему менять файл. Сравните предложение с прямым редактированием.

## Проверка результата

Вы умеете проверять состояние репозитория, читать diff, отличать рабочие изменения от staged-изменений, добавлять только нужные файлы, обнаруживать нежелательные изменения и откатывать их через `git restore`, а также объяснять, почему результат агента нельзя принимать автоматически.
